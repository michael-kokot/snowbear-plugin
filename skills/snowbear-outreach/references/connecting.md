## Connecting
- Base URL: https://mrnihnyyyhorznwzebep.supabase.co/functions/v1/snowbear-api/v1
- REST agents authenticate with an OAuth Bearer token through https://www.snowbear.ai/api/v1, using that public URL as the OAuth resource. Personal integrations may use the `X-API-Key` header directly on the API base. MCP OAuth credentials are managed by the connected client and authorize MCP only; they cannot authenticate REST calls. REST OAuth can use https://www.snowbear.ai/oauth/authorize/api as its authorization URL without a resource parameter; alternatively, the general authorization URL requires https://www.snowbear.ai/api/v1 as the resource (omitting it there defaults to MCP). Token exchange and refresh can omit resource and retain the original approved audience; an explicit different resource is rejected. OAuth access tokens are renewed using the returned rotating refresh token; a client with private credential persistence and refresh support does not need a separate manual token just for scheduled work. Device approval remains incomplete until the initiating client redeems its private device_code at the token endpoint. SNOWBEAR_API_KEY is the documented environment variable for manual REST tokens.
- Use curl or any HTTP client. Requests and responses are JSON.
- Errors look like {"error": {"code": "...", "message": "...", "request_id": "..."}}. Show me the message when something fails, and the request_id if it says to contact support. A 409 or 402 means SnowBear refused for a reason I can fix (for example LinkedIn not connected, or billing); explain it rather than retrying.
- Limits: 100 reads and 20 writes every 10 seconds for my account. On a 429, or a 500 that says to retry, wait the number of seconds in the Retry-After header, then retry; after a few failed tries, stop and tell me. Never retry in a tight loop.
- Every response puts its result under "data": one object for a single item, an array for a list. The fields listed below are inside data. A few lists also return a "summary" object next to data (counts for the whole list).
- Paged lists (campaigns, sequences, contacts, approvals, activities, companies, lists, list people, referral searches, pages) also return "has_more" and "next_cursor". Pass ?cursor=<next_cursor> for the next page. Pages hold up to 200 items (?limit=, default 100) unless an endpoint below says less. When has_more is false you have everything.
- Writes that take a "contacts" list accept up to 25 people per call (10 for referral pages and team invitations) and return one result per person, in the order sent, each with an "outcome" and a "message" saying what happened and what to do next. The response also has a top-level "message" summing up the batch (counts per outcome, and anything that needs fixing).
- Other writes (creating or changing a campaign, sequence, list, page) return a top-level "message" too: what changed and the usual next step. Errors' messages name the field or value that was wrong and how to fix it. Read these messages and relay the useful part to me rather than guessing.
- A person's id is "id" on their contact row and "contact_id" everywhere else (approvals, activities, results, sequence reads). It's the same value every {contact_id} path takes.
- Responses can include more fields than listed here. Use them when they help.
- Some results carry an explanation {code, message, fixable_by}. Show me message; codes are for your logic. When fixable_by is snowbear or none, don't ask me to do anything.
- A read with a query parameter it doesn't take still answers, with a "warnings" entry (unknown_query_parameter) naming what it ignored and what it takes. When you see one, the results aren't filtered the way you meant: fix the parameter and ask again.
- When account identity is needed for my request, GET /me confirms it and its scopes. A read-only connection cannot change outreach; reconnect with write scope when a requested change requires it.
